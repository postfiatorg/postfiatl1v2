# Public RPC Operator Policy

Status: controlled-testnet policy, 2026-05-13.

This runbook is the source of truth for exposing PostFiat L1 RPC. Validator
processes never bind their plaintext RPC listener to a public or wildcard
address. Public clients terminate TLS and authenticate at a separately managed
edge, which forwards to the validator's loopback listener. Signed write
admission and Orchard batch creation remain explicit, bounded opt-ins.

## Default Service

Provisioned validators run `postfiat-node rpc-serve` from the generated
systemd unit:

```bash
postfiat-node rpc-serve \
  --data-dir /var/lib/postfiat/validator-N \
  --bind-host 127.0.0.1 \
  --port <rpc_port> \
  --max-requests ${POSTFIAT_RPC_MAX_REQUESTS} \
  --timeout-ms ${POSTFIAT_TIMEOUT_MS} \
  --child-timeout-ms ${POSTFIAT_RPC_CHILD_TIMEOUT_MS} \
  --event-log /var/log/postfiat/validator-N/rpc-events.ndjson
```

Controlled-testnet defaults are generated by the release generator
(`crates/node/src/batch_snapshot.rs`, see
[signed deployment manifest](signed-deployment-manifest.md)); the example unit
`systemd/postfiat-rpc.service.example` carries the same values:

| Setting | Default | Policy |
| --- | ---: | --- |
| RPC port | `RPC_BASE_PORT + validator_index` (`27650+`) | Open only for approved testnet peers, monitoring, and public read clients. |
| Bind host | `127.0.0.1` | Mandatory. The node rejects public, wildcard, and hostname binds even if the legacy public-bind environment variable is present. |
| `POSTFIAT_RPC_MAX_REQUESTS` | `100000` | Bounded lifecycle cap. At the budget `rpc-serve` stops accepting, finishes in-flight connections, writes its end-of-run report while the port is still bound and exits 0; systemd (`Restart=always`, `RestartSec=1`) starts it again about a second later. |
| `POSTFIAT_TIMEOUT_MS` | `30000` | Per-connection socket timeout. |
| `POSTFIAT_RPC_CHILD_TIMEOUT_MS` | `30000` | Child command execution timeout; timeout is reported as `rpc_child_timeout`. |
| Event log | `rpc-events.ndjson` | Required. Ship or retain with validator logs. |
| Transparent write methods | Disabled | Do not pass `--allow-mempool-submit` on public validator RPC by default. |
| Orchard batch creation | Disabled | Do not pass `--allow-orchard-batch-create` on public validator RPC by default. If enabled, only bounded inline JSON batch creation is admitted, direct shielded apply remains disabled, and `--max-orchard-batch-create-concurrent` must remain bounded. |
| Private action admission | Disabled | `--allow-private-action-admission` exposes `private_action_submit` and `private_action_receipt` and starts the round service, which dispatches reserved user-proven batches with this validator's `--finality-key-file` and `--finality-topology` through the `shield_batch_finality` round. Startup fails if those files are missing. Admission records live in `<data-dir>/private_action_admission/`. Keep it off until a release and governance enable atomic shielded batches. |

`private_readiness` on a server reports the switch as `on` or `off` in
`admission_switch.state`. The value is the server's own setting, never a
request parameter. A local `postfiat-node rpc --method private_readiness`
reports `unknown`. The switch never changes `ready`.

`custody` says who published the report and with what custody. Each fact
comes from the serving process, never from the request, and each unmet fact
is a reason that keeps `ready` false:

| Field | Source | Reason when unmet |
| --- | --- | --- |
| `published_by` | `rpc_serve` from the running server; `local_read` from `postfiat-node rpc`, whose `--data-dir` may be a copy | `readiness_not_published_by_running_service` |
| `store_backend`, `transactional_active` | the backend-mode record of the server's own `--data-dir` (`transactional` when absent) and whether its transactional store is active, as the node decides it | `store_not_transactional` (a JSONL store, a plain `init` store or a transactional store before its activation height) |
| `validator_signer` | `none` with neither `--allow-mempool-submit-finality` nor `--allow-private-action-admission`; otherwise `plaintext_key_file` (`--finality-key-file`) or `socket` (`--finality-signer-socket`, a [validator signer process](#validator-signer-process)), with `signer_socket` and `signer_uid`, the uid the kernel reports for the signer when it answers during the read, beside the server's own `serving_uid` | `validator_signer_none`, `validator_signer_unsafe_file`; for `socket`, `validator_signer_same_user` when `signer_uid` equals `serving_uid` and `validator_signer_unreachable` when the signer does not answer |
| `key_files` | per key file the key-file signer uses (none for `socket`) (`--finality-key-file`, and `--finality-proposal-key-file` when it differs): `owner_only` when owned by the serving user with no group or other access | `validator_key_file_not_owner_only`, `validator_key_file_missing`, `validator_key_file_unreadable` |

Only the socket signer under its own user can satisfy the signer facts;
`plaintext_key_file` never does. Two cases are not detected by the node and are deployment checks:
an owner-only key file read by a gateway running as the same user (run
separate users), and an rpc-serve over a copied data directory (serve from
the validator's live store).

### Validator signer process

`postfiat-node validator-signer-serve` holds the validator key so rpc-serve
does not. It loads `--key-file` (and `--proposal-key-file`, default the
same), listens on `--socket` with mode `0600`, and answers only peers whose
kernel-reported uid is in `--allow-peer-uid` (repeatable); any other peer is
refused before its request is read. Each request is one length-prefixed JSON
frame (at most 9 MiB, the hex of a 4 MiB transport frame) with a deadline
(`--deadline-ms`, default 5000). It signs only what rpc-serve signs as the
validator: block certificate, block timeout and consensus-v2 votes and the
transport envelopes that carry them with the vote key, and block and
consensus-v2 proposals with the proposal key. `describe` returns the public
keys and the signer's uid; no answer contains key material.

rpc-serve takes `--finality-signer-socket <path>` instead of
`--finality-key-file` and `--finality-proposal-key-file`; passing both is
refused. At startup the signer must answer and hold, for both roles, the key
the validator registry records for this node, or rpc-serve does not start
(`validator_signer_key_mismatch`, `validator_signer_unreachable`). A signer
that later stops answering or times out fails that request
(`validator_signer_unreachable`, `validator_signer_timeout`); nothing falls
back to a key file, and rpc-serve does not read `<data-dir>/validator_keys.json`.

Deployment shape: two units and two users. The signer unit runs as its own
user (for example `postfiat-signer`), owns the key file (`0600`) and a socket
directory such as `/run/postfiat-signer` (`0750`, group shared with the
serving user so it can reach the socket), and passes `--allow-peer-uid` with
the rpc-serve user's uid. The rpc-serve unit runs as `postfiat`, cannot read
the key file, and passes `--finality-signer-socket
/run/postfiat-signer/<validator>.sock`. Start the signer first. Readiness
reports `validator_signer_same_user` when both units run as one user.

### Resolving a stuck private action record

A crash between dispatch and the certified send leaves an admission record
`unknown`. The round service settles it when its batch lands on chain and
never dispatches it again. If it does not land, resolve it on the validator
that holds it:

```bash
postfiat-node private-action-resolve --data-dir <data-dir> --intent-id <96-hex>
postfiat-node private-action-resolve --data-dir <data-dir> --intent-id <96-hex> \
  --abandon --reason "<why>"
```

- **Without `--abandon`:** the command re-reads the chain for the record's
  batch. If the batch is there, it settles the record as accepted or rejected.
  Otherwise it prints the record and changes nothing.
- **With `--abandon`:** the command marks a `queued` or `unknown` record
  `abandoned`, with the reason and the operator's Unix time, but only if the
  batch is not on chain. It refuses `dispatched` (a round may still be
  settling), final records, and a batch already on chain.
- **No round runs alongside it:** the command holds the admission store lock,
  so no round-service pass, and so no round, runs while it works.
- **After abandoning:** the wallet may resubmit the same bytes. That creates a
  fresh `queued` record under the same intent. The action-hash and batch-id
  indexes keep pointing at that intent, and the abandoned record stays in
  `<data-dir>/private_action_admission/records.jsonl` for audit.
- **Every run:** the command never dispatches a record, and its output
  includes the intent's full record history.

## RPC Round-Trip Health Probe

Run one read-only `status` exchange against the loopback RPC listener:

```bash
postfiat-node rpc-probe --host 127.0.0.1 --port <rpc_port> --timeout-ms 5000
PYTHONPATH=python python3 -m postfiat_rpc.rpc_probe \
  --endpoint 127.0.0.1:<rpc_port> --timeout-seconds 5
```

Both commands use one connection, send one newline-delimited request, shut down
its write side, and exit `0` only for a valid `ok:true` status response within
the timeout. Success prints `height`, a 12-character `tip` prefix, and
`round_trip_ms`. Exit `1` prints a one-line reason (connect refused, connect
timeout, no response, malformed response, or `ok:false`). The commands never
retry; a timer or operator decides when to probe again. `rpc-serve` also bounds
an idle keep-alive connection by its `--timeout-ms` per-request read deadline
(capped at 30 seconds), including the wait for the next frame.

## Allowed Read Surface

Read-only `rpc-serve` accepts:

- Node and ledger status: `status`, `server_info`, `metrics`, `ledger`.
- Account and transaction reads: `account`, `receipts`, `tx`, `blocks`,
  `batch_archive`.
- Validator/governance reads: `validators`, `manifests`, `verify_state`,
  `verify_blocks`, `verify_bridge`, `verify_mempool`, `verify_shielded`.
- Mempool/shield/bridge reads: `mempool_status`, `shield_scan`,
  `shield_disclose`, `shield_turnstile`, `bridge_status`.
- Fee reads: `fee`, `transfer_fee_quote`.

`manifests` reports `available=false` unless
`governance-genesis-bundle.json` is present in the validator data directory and
its referenced operator manifest files verify. That is intentional: a node must
not invent operator metadata if the canonical bundle is absent.

## Write Opt-In

`mempool_submit_signed_transfer` is the only remote transparent write admitted
by `rpc-serve`, and only when all of the following are true:

- The service is started with `--allow-mempool-submit`.
- `--max-mempool-submit-per-peer` is set to a positive bounded value.
- `--max-mempool-submit-total` is set to a positive bounded value.
- Invalid-signature, duplicate-transaction, peer-limit, and global-limit
  counters are monitored from the `postfiat-rpc-serve-v1` report.
- A valid read after pressure is tested before the endpoint is advertised.

Use a dedicated authenticated write edge. Do not expose the validator process
directly as a fallback.

## Orchard Batch-Creation Opt-In

`shield_batch_orchard` and `shield_batch_orchard_withdraw` are admitted by
`rpc-serve` only when the service is started with
`--allow-orchard-batch-create`.

This mode is deliberately narrower than public shielded apply:

- Requests must carry bounded `action_json`; server-local `action_file` and
  client-selected `batch_file` paths are rejected.
- The server writes action/batch artifacts only under its controlled spool
  directories.
- Each request runs through the existing `--child-timeout-ms` child-process
  boundary.
- Operators must set positive `--max-orchard-batch-create-per-peer` and
  `--max-orchard-batch-create-total` limits.
- Operators must set positive `--max-orchard-batch-create-concurrent`; the
  controlled-testnet default is `1`, so excess simultaneous verifier work fails
  before a child verifier starts.
- `apply_shield_batch` is not admitted by `rpc-serve`.

Current evidence:
`reports/testnet-orchard-rpc-batch-create/orchard-rpc-batch-create-v0-20260515T111516Z/testnet-orchard-rpc-batch-create.json`
from `scripts/testnet-orchard-rpc-batch-create-smoke`.
Concurrent malformed-edge evidence:
`reports/testnet-orchard-rpc-malformed-edge-load/orchard-rpc-malformed-edge-load-v0-20260515T113620Z/testnet-orchard-rpc-malformed-edge-load.json`
from `scripts/testnet-orchard-rpc-malformed-edge-load-smoke`. That run
proved three concurrent exact-size malformed proof actions fail closed without

## Logs And Retention

Operators must retain:

- `/var/log/postfiat/validator-N/rpc-events.ndjson`
- `/var/log/postfiat/validator-N/stdout.log`
- `/var/log/postfiat/validator-N/stderr.log`
- systemd journal entries for `postfiat-validator-N-rpc.service`

Minimum retention for controlled testnet is the greater of seven days or the
current evidence window. If partial-history pruning is enabled, retain RPC logs
through the archive handoff window so `tx`, `ledger`, and `history-status`
answers can be correlated with archive evidence.

## Edge And Firewall Posture

Do not open the validator RPC port publicly. A public load balancer or reverse
proxy must reach it over loopback, a Unix socket, or a private authenticated
overlay and must enforce:

- connection and request-rate limits;
- request body limits at or below `MAX_RPC_REQUEST_BYTES` (`65536`);
- TLS termination for public Internet access;
- access logs with source IP, method, status, and response class;
- no request rewriting that changes JSON request bodies.

Validator-to-validator plaintext transport likewise binds only to explicit
private-overlay IP addresses. Public topology IPs, DNS names, and wildcard
binds fail closed during deployment staging and process startup. Public routing
to that overlay is an operator misconfiguration, not a supported deployment.

## Verification Commands

Before advertising an endpoint:

```bash
scripts/testnet-rpc-read-alias-smoke
scripts/testnet-rpc-serve-tamper
scripts/testnet-rpc-write-edge-load-smoke   # only for write-edge services
```

The readiness gate requires the read-alias smoke and the P0 gate refuses a
local readiness report that omits it.
