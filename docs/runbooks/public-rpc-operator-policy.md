# Public RPC Operator Policy

Status: controlled-testnet policy, 2026-05-13.

This runbook is the source of truth for exposing PostFiat L1 RPC. Validator
processes never bind their plaintext RPC listener to a public or wildcard
address. Public clients terminate TLS and authenticate at a separately managed
edge, which forwards to the validator's loopback listener. Signed write
admission and Orchard batch creation remain explicit, bounded opt-ins.

## Default Service

Provisioned validators run `postfiat-node rpc-serve` from the generated
systemd unit:

```bash
postfiat-node rpc-serve \
  --data-dir /var/lib/postfiat/validator-N \
  --bind-host 127.0.0.1 \
  --port <rpc_port> \
  --max-requests ${POSTFIAT_RPC_MAX_REQUESTS} \
  --timeout-ms ${POSTFIAT_TIMEOUT_MS} \
  --child-timeout-ms ${POSTFIAT_RPC_CHILD_TIMEOUT_MS} \
  --event-log /var/log/postfiat/validator-N/rpc-events.ndjson
```

Controlled-testnet defaults are generated by the release generator
(`crates/node/src/batch_snapshot.rs`, see
[signed deployment manifest](signed-deployment-manifest.md)); the example unit
`systemd/postfiat-rpc.service.example` carries the same values:

| Setting | Default | Policy |
| --- | ---: | --- |
| RPC port | `RPC_BASE_PORT + validator_index` (`27650+`) | Open only for approved testnet peers, monitoring, and public read clients. |
| Bind host | `127.0.0.1` | Mandatory. The node rejects public, wildcard, and hostname binds even if the legacy public-bind environment variable is present. |
| `POSTFIAT_RPC_MAX_REQUESTS` | `100000` | Bounded lifecycle cap. At the budget `rpc-serve` stops accepting, finishes in-flight connections, writes its end-of-run report while the port is still bound and exits 0; systemd (`Restart=always`, `RestartSec=1`) starts it again about a second later. |
| `POSTFIAT_TIMEOUT_MS` | `30000` | Per-connection socket timeout. |
| `POSTFIAT_RPC_CHILD_TIMEOUT_MS` | `30000` | Child command execution timeout; timeout is reported as `rpc_child_timeout`. |
| Event log | `rpc-events.ndjson` | Required. Ship or retain with validator logs. |
| Transparent write methods | Disabled | Do not pass `--allow-mempool-submit` on public validator RPC by default. |
| Orchard batch creation | Disabled | Do not pass `--allow-orchard-batch-create` on public validator RPC by default. If enabled, only bounded inline JSON batch creation is admitted, direct shielded apply remains disabled, and `--max-orchard-batch-create-concurrent` must remain bounded. |
| Private action admission | Disabled | `--allow-private-action-admission` exposes `private_action_submit` and `private_action_receipt` and starts the round service, which dispatches reserved user-proven batches with this validator's `--finality-key-file` and `--finality-topology` through the `shield_batch_finality` round. Startup fails if those files are missing. Admission records live in `<data-dir>/private_action_admission/`. Keep it off until a release and governance enable atomic shielded batches. |

`private_readiness` on a server reports the switch as `on` or `off` in
`admission_switch.state`. The value is the server's own setting, never a
request parameter. A local `postfiat-node rpc --method private_readiness`
reports `unknown`. The switch never changes `ready`.

`custody` says who published the report and with what custody. Each fact
comes from the serving process, never from the request, and each unmet fact
is a reason that keeps `ready` false:

| Field | Source | Reason when unmet |
| --- | --- | --- |
| `published_by` | `rpc_serve` from the running server; `local_read` from `postfiat-node rpc`, whose `--data-dir` may be a copy | `readiness_not_published_by_running_service` |
| `store_backend`, `transactional_active` | the backend-mode record of the server's own `--data-dir` (`transactional` when absent) and whether its transactional store is active, as the node decides it | `store_not_transactional` (a JSONL store, a plain `init` store or a transactional store before its activation height) |
| `validator_signer` | `none` with neither `--allow-mempool-submit-finality` nor `--allow-private-action-admission`; otherwise `plaintext_key_file` (`--finality-key-file`) or `socket` (`--finality-signer-socket`, a [validator signer process](#validator-signer-process)), with `signer_socket` and `signer_uid`, the uid the kernel reports for the signer when it answers during the read, beside the server's own `serving_uid`, `signer_key_matches`, whether the keys the signer describes for both roles are the ones the validator registry records (`null` when the registry cannot be read), and `validator_registry_readable`, whether the registry could be read for that comparison | `validator_signer_none`, `validator_signer_unsafe_file`; for `socket`, `validator_signer_same_user` when `signer_uid` equals `serving_uid`, `validator_signer_unreachable` when the signer does not answer, `validator_signer_key_mismatch` when `signer_key_matches` is false, and `validator_registry_unreadable` when `validator_registry_readable` is false |
| `key_files` | per key file the key-file signer uses (none for `socket`) (`--finality-key-file`, and `--finality-proposal-key-file` when it differs): `owner_only` when owned by the serving user with no group or other access | `validator_key_file_not_owner_only`, `validator_key_file_missing`, `validator_key_file_unreadable` |

Only the socket signer under its own user can satisfy the signer facts;
`plaintext_key_file` never does. Two cases are not detected by the node and are deployment checks:
an owner-only key file read by a gateway running as the same user (run
separate users), and an rpc-serve over a copied data directory (serve from
the validator's live store).

### Validator signer process

`postfiat-node validator-signer-serve` holds the validator key so rpc-serve
does not. It loads `--key-file` (and `--proposal-key-file`, default the
same), listens on `--socket` with mode `0660` (with `--socket-group <name or gid>`,
the socket's group is set to that group; without it the group is the signer's
primary group), and answers only peers whose kernel-reported uid is in
`--allow-peer-uid` (repeatable); any other peer is refused before its
request is read. On Linux a connect to a Unix socket needs write permission
on the socket file, so the serving user reaches it through the group; the uid
allow-list is the real gate. Each request is one length-prefixed JSON
frame (at most 1 MiB: the largest message signed is a proposal, about 100 KB
at the batch cap and at most 6.2 KB on devnet-2 so far, sent as hex) with a deadline
(`--deadline-ms`, default 5000). It signs under the contexts rpc-serve
signs with as the validator: block certificate, block timeout and
consensus-v2 votes and the transport envelopes that carry them with the vote
key, and block and consensus-v2 proposals with the proposal key; any other
context is refused. `describe` returns the public keys and the signer's uid;
no answer contains key material.

The signer requires `--state-dir <persistent-directory>`. It decodes consensus
messages by their signing context, binds the validator identity to the held key,
and persists a round floor and message digest before signing. Identical retries
at that floor are allowed; a different message at the same height/view and any
older round are refused. Prepare and precommit, and votes and timeouts, have
separate floors. Key aliases, committee changes and protocol version changes
cannot reset a floor. The guard signs for one chain domain, fixed at
initialization: a request naming another chain id or genesis hash is refused
(`validator_signer_domain_refused`) and leaves nothing in the state. Transport
authentication uses a separate signing domain and has no consensus slot.

For a **new, never-used custody instance**, pass `--initialize-state
--chain-id <ID> --genesis-hash <HASH>` once with a nonexistent state directory.
Remove `--initialize-state` from the service unit; keeping `--chain-id` and
`--genesis-hash` there makes a restart refuse a guard of another chain
(`validator_signer_state_domain_mismatch`). Restart requires the existing state
and lock; missing, corrupt, shared or wrong-key state is refused. The directory
is `0700`, files are `0600`, all owned by the signer; its parents must not let another user replace it. State is atomically replaced
and both the file and directory are synced. A persistence failure disables
signing until operator inspection and restart. An exclusive process lock and a
request mutex serialize reservations; the mutex is held across both syncs, so
`describe` and transport signing wait for a reservation in flight (latency
only). Opening the state removes `state.*.tmp` files a crash left before rename.

Never delete, restore an older copy of, or initialize a replacement guard for
usable keys. An empty guard cannot reconstruct past votes, so a key that already
signed (an existing validator moving from `--finality-key-file` to the socket)
is initialized with a floor: add `--min-height <N>` to the initialization. Every
consensus round below `N` is then refused as `validator_signer_stale_round`, also after restart; the floor is set
only at initialization. To choose `N`, stop the old signer and rpc-serve first,
then take the larger of the store's finalized height plus one (`status`) and the
highest height in the store's vote-lock index (`block_proposal_vote_locks`)
plus one. That index holds block votes only: if the old signer may have voted or
timed out on a height that is not final yet, read the tip after the other
validators have finalized past it. A floor can only refuse more requests: a value too high costs liveness
until the chain passes it, never safety. Key-set changes require their own
reviewed transition. A process allowed on the socket can still raise a floor
out of reach, for example by one vote near the maximum height: nothing resets a
floor, so recovery from such poisoning is rotating the validator key. This is a
signing-slot guard, not the consensus lock/QC state machine: it does not prove
that a new round's vote is justified. The signer user/root can still compromise custody.

rpc-serve takes `--finality-signer-socket <path>` instead of
`--finality-key-file` and `--finality-proposal-key-file`; passing both is
refused. At startup the signer must answer and hold, for both roles, the key
the validator registry records for this node, or rpc-serve does not start
(`validator_signer_key_mismatch`, `validator_signer_unreachable`). A signer
that later stops answering or times out fails that request
(`validator_signer_unreachable`, `validator_signer_timeout`); nothing falls
back to a key file, and rpc-serve does not read `<data-dir>/validator_keys.json`.

Deployment shape: three units and two users. The signer unit runs as its own
user (for example `postfiat-signer`) and owns the key file (`0600`) and a
socket directory such as `/run/postfiat-signer` (`0750`, group
`postfiat-signer-clients`, which the serving user is a member of). It passes
`--socket-group postfiat-signer-clients`, so the socket is `0660` in that
group, and `--allow-peer-uid` with the clients' uid. The RPC and transport units
run as `postfiat`, cannot read
the key file, and pass `--finality-signer-socket
/run/postfiat-signer/<validator>.sock`. Start the signer first. Readiness
reports `validator_signer_same_user` when the signer and RPC run as one user.
It also reports `signer_double_sign_protection`; false or absent yields
`validator_signer_guard_unavailable`. RPC startup refuses an unguarded signer.
In socket mode `data_dir_key_files` lists `validator_keys.json` or
`node/validator_keys.json` left in the serving data directory, and any entry
yields `validator_key_copy_in_data_dir`: rpc-serve could read that copy and sign
outside the guard. Move the key, do not copy it.

Keep guard state outside the RPC user's data directory, for example
`/var/lib/postfiat-signer/validator-0/guard`, and allow that path in the signer's
systemd write sandbox. Add `--state-dir` to the signer unit; never put
`--initialize-state` in its restart command. Existing release units still need
the explicit two-user/socket transition below.

The Python deployment check reads process identities, executable hashes, the
actual open database, custody permissions and a fresh `private_readiness` reply.
It fails when a file named `validator_keys.json`, or named like the signer's
key files, exists anywhere under the data directory, and when the rpc or gateway
process holds any capability (`CapEff`, `CapPrm` or `CapAmb` nonzero, for example
`CAP_DAC_READ_SEARCH` granted by systemd `AmbientCapabilities`).
With `--search-root DIR...` it also fails, listing them under
`readable_key_copies`, when a file named like a key file outside the signer's
directory is readable by the rpc or gateway uid by its mode bits and group
membership: the owner, group and other read bits on the file and the search
bits on every ancestor. POSIX ACLs are not inspected, and no file is read.
It requires permission to inspect all three processes, normally root:

```sh
PYTHONPATH=python python3 -m postfiat_ops.validator_signer_check \
  --signer-pid SIGNER_PID --rpc-pid RPC_PID --gateway-pid GATEWAY_PID \
  --rpc-port RPC_PORT --node-sha256 EXPECTED_NODE_SHA256 \
  --data-dir EXPECTED_LIVE_DATA_DIR --database EXPECTED_LIVE_REDB_FILE \
  --key-file SIGNER_KEY_FILE --state-dir SIGNER_GUARD_DIR \
  --socket SIGNER_SOCKET --output NEW_REPORT_DIRECTORY \
  [--search-root /var/lib/postfiat BACKUP_DIRECTORY...]
```

Review `report.json` or `review.html`. Exit 2 means a failed or unavailable check;
it is never a pass. Pin the intended live paths from the deployment manifest:
supplying a copy's path cannot establish a live-store deployment. The gateway
must use a third unprivileged UID and have no protected files open. This is a
point-in-time observation, not proof of every past/future access or a memory
secret scan. Governance readiness and rollout approval are separate.

#### Two-user units

`deployment-validator-units-stage --signer-shape two-user` writes the two-user
shape into the release packet (`deployment_signer_unit`, `deployment_rpc_unit`
and `deployment_transport_unit` in `crates/node/src/batch_snapshot.rs`).
Without the option the packet keeps the single-user units, byte for byte.

- `postfiat-<validator>-signer.service` runs `validator-signer-serve` as
  `postfiat-signer` (group `postfiat-signer-clients`) with the key file and the
  guard under `/var/lib/postfiat-signer/<validator>` (`0700`), the topology's
  chain id and genesis hash, and the socket
  `/run/postfiat-signer/<validator>.sock` (directory `0750`). It allows the uid
  in `POSTFIAT_SIGNER_ALLOW_PEER_UID`, read from the host file
  `/etc/postfiat/signer/<validator>.env`. It has no capabilities and no
  network, and it never initializes the guard. One signer process serves both
  clients, rpc-serve and the transport validator: both run as `postfiat`, so
  the one allowed uid covers them, and the signer already accepts every
  context they sign (below).
- `postfiat-<validator>-rpc.service` is the single-user rpc unit with
  `--finality-signer-socket` instead of both key-file flags,
  `SupplementaryGroups=postfiat-signer-clients`, and `Requires=`/`After=` the
  signer unit.
- `postfiat-<validator>.service` is the single-user transport unit with
  `transport-validator-serve --finality-signer-socket` instead of
  `--unsafe-devnet-file-signer --key-file <data-dir>/validator_keys.json`, and
  the same group and ordering.

The signer unit is not in the signed bindings; its binary is checked by the
same `deployment-manifest-verify` before it starts.

`transport-validator-serve --finality-signer-socket PATH` replaces both
`--key-file` and `--unsafe-devnet-file-signer` (`validator_signer_flags_conflict`
with either). Before it binds, the signer must answer and hold the registered
key, and in socket mode the process reads no key file
(`validator_signer_file_refused_in_socket_mode`). Every signature it makes goes
through the signer: block votes and proposal signatures, consensus-v2
proposals and prepare and precommit votes (the guard decodes these), and the
transport envelope authentication on its responses, which the guard passes
through by design. The key therefore moves out of the data directory, and
readiness no longer reports `validator_key_copy_in_data_dir`
(`crates/node/tests/validator_signer_two_user_units_process.rs` starts the
three processes from the generated units on a local chain). That test checks
startup and readiness only: it does not make the transport process sign
anything through the socket, so the qualification run must show such a
signature (a certified round with the signer).

Order on a validator (the deploy sheet uses the same steps, word for word). `shred -u` in the sheet's move is best effort on a journaled filesystem; the search step and the checker's `--search-root` find files, not freed blocks.

1. Create `postfiat-signer` and `postfiat-signer-clients`, add `postfiat` to the group, and write `/etc/postfiat/signer/<validator>.env` with `POSTFIAT_SIGNER_ALLOW_PEER_UID=$(id -u postfiat)`.
2. Stop both old units, `postfiat-<validator>.service` and `postfiat-<validator>-rpc.service`: both sign with the key.
3. Search for other copies of the key that `postfiat` can read, outside the signer's directory; the move is complete only when the search finds nothing.
4. Move the key to `/var/lib/postfiat-signer/<validator>/validator_keys.json` (`0600`, owned by `postfiat-signer`); no copy stays in the data directory.
5. Choose the floor `N` by the rule above, with both old units stopped.
6. Initialize the guard once as `postfiat-signer` with `--initialize-state --min-height N` and a throwaway `--socket` under the signer's directory; stop it after its ready line.
7. Start the signer unit, then the transport and rpc units.
8. Run the deployment check.
9. Read `private_readiness` and record `custody_reasons`.

The search runs as `postfiat` over every mounted filesystem except `/proc`, `/sys`, `/dev` and `/run`, whatever the files' owner: `find -readable` lists the files named like key files that `postfiat` can read, and `grep -l` lists the files `postfiat` can read that hold `private_key_hex` and this key's public key; both print names only.

The [deploy sheet template](validator-signer-two-user-deploy-sheet.md) carries
these steps with the commands.

At start the signer probes an existing file at `--socket`. If something
still listens on it, the signer refuses to start
(`validator_signer_socket_in_use`). A stale socket file is replaced, and
anything that is not a socket is never replaced
(`validator_signer_socket_path_not_a_socket`). An accept error does not stop
the signer: it logs the first error and then at most one line per second,
and retries after 50 ms.

In socket mode rpc-serve, and every child process it starts, refuses to
read any key file (`validator_signer_file_refused_in_socket_mode`). The
signer is looked up by the canonical path of the socket and the data
directory.

Typed codes:

| Code | Meaning |
|---|---|
| `validator_signer_unreachable` | The signer does not accept the connection, or writing the request fails. |
| `validator_signer_timeout` | The request passed its deadline (`--deadline-ms` on the signer, 5 s on rpc-serve). |
| `validator_signer_peer_refused` | The peer's uid is not in `--allow-peer-uid`; the request was not read. |
| `validator_signer_busy` | The signer already serves 32 connections. |
| `validator_signer_request_too_large` | The request frame exceeds 1 MiB. |
| `validator_signer_protocol` | A malformed frame, schema, method or field. |
| `validator_signer_context_refused` | The signer does not sign under that context. |
| `validator_signer_key_missing` | The signer holds no key for that validator. |
| `validator_signer_sign_failed` | Signing failed inside the signer. |
| `validator_signer_key_mismatch` | The signer's key is not the registry's: at startup, on a signature, or in readiness. |
| `validator_signer_bad_signature` | The answered signature does not verify under the described key. |
| `validator_signer_flags_conflict` | `--finality-signer-socket` was given with a key-file flag. |
| `validator_signer_file_refused_in_socket_mode` | A key file read was refused in socket mode. |
| `validator_signer_socket_in_use` | A live signer already listens on `--socket`. |
| `validator_signer_socket_path_not_a_socket` | `--socket` names a file that is not a socket; it is left as it is. |

### Resolving a stuck private action record

A crash between dispatch and the certified send leaves an admission record
`unknown`. The round service settles it when its batch lands on chain and
never dispatches it again. If it does not land, resolve it on the validator
that holds it:

```bash
postfiat-node private-action-resolve --data-dir <data-dir> --intent-id <96-hex>
postfiat-node private-action-resolve --data-dir <data-dir> --intent-id <96-hex> \
  --abandon --reason "<why>"
```

- **Without `--abandon`:** the command re-reads the chain for the record's
  batch. If the batch is there, it settles the record as accepted or rejected.
  Otherwise it prints the record and changes nothing.
- **With `--abandon`:** the command marks a `queued` or `unknown` record
  `abandoned`, with the reason and the operator's Unix time, but only if the
  batch is not on chain. It refuses `dispatched` (a round may still be
  settling), final records, and a batch already on chain.
- **No round runs alongside it:** the command holds the admission store lock,
  so no round-service pass, and so no round, runs while it works.
- **After abandoning:** the wallet may resubmit the same bytes. That creates a
  fresh `queued` record under the same intent. The action-hash and batch-id
  indexes keep pointing at that intent, and the abandoned record stays in
  `<data-dir>/private_action_admission/records.jsonl` for audit.
- **Every run:** the command never dispatches a record, and its output
  includes the intent's full record history.

## RPC Round-Trip Health Probe

Run one read-only `status` exchange against the loopback RPC listener:

```bash
postfiat-node rpc-probe --host 127.0.0.1 --port <rpc_port> --timeout-ms 5000
PYTHONPATH=python python3 -m postfiat_rpc.rpc_probe \
  --endpoint 127.0.0.1:<rpc_port> --timeout-seconds 5
```

Both commands use one connection, send one newline-delimited request, shut down
its write side, and exit `0` only for a valid `ok:true` status response within
the timeout. Success prints `height`, a 12-character `tip` prefix, and
`round_trip_ms`. Exit `1` prints a one-line reason (connect refused, connect
timeout, no response, malformed response, or `ok:false`). The commands never
retry; a timer or operator decides when to probe again. `rpc-serve` also bounds
an idle keep-alive connection by its `--timeout-ms` per-request read deadline
(capped at 30 seconds), including the wait for the next frame.

## Allowed Read Surface

Read-only `rpc-serve` accepts:

- Node and ledger status: `status`, `server_info`, `metrics`, `ledger`.
- Account and transaction reads: `account`, `receipts`, `tx`, `blocks`,
  `batch_archive`.
- Validator/governance reads: `validators`, `manifests`, `verify_state`,
  `verify_blocks`, `verify_bridge`, `verify_mempool`, `verify_shielded`.
- Mempool/shield/bridge reads: `mempool_status`, `shield_scan`,
  `shield_disclose`, `shield_turnstile`, `bridge_status`.
- Fee reads: `fee`, `transfer_fee_quote`.

`manifests` reports `available=false` unless
`governance-genesis-bundle.json` is present in the validator data directory and
its referenced operator manifest files verify. That is intentional: a node must
not invent operator metadata if the canonical bundle is absent.

## Write Opt-In

`mempool_submit_signed_transfer` is the only remote transparent write admitted
by `rpc-serve`, and only when all of the following are true:

- The service is started with `--allow-mempool-submit`.
- `--max-mempool-submit-per-peer` is set to a positive bounded value.
- `--max-mempool-submit-total` is set to a positive bounded value.
- Invalid-signature, duplicate-transaction, peer-limit, and global-limit
  counters are monitored from the `postfiat-rpc-serve-v1` report.
- A valid read after pressure is tested before the endpoint is advertised.

Use a dedicated authenticated write edge. Do not expose the validator process
directly as a fallback.

## Orchard Batch-Creation Opt-In

`shield_batch_orchard` and `shield_batch_orchard_withdraw` are admitted by
`rpc-serve` only when the service is started with
`--allow-orchard-batch-create`.

This mode is deliberately narrower than public shielded apply:

- Requests must carry bounded `action_json`; server-local `action_file` and
  client-selected `batch_file` paths are rejected.
- The server writes action/batch artifacts only under its controlled spool
  directories.
- Each request runs through the existing `--child-timeout-ms` child-process
  boundary.
- Operators must set positive `--max-orchard-batch-create-per-peer` and
  `--max-orchard-batch-create-total` limits.
- Operators must set positive `--max-orchard-batch-create-concurrent`; the
  controlled-testnet default is `1`, so excess simultaneous verifier work fails
  before a child verifier starts.
- `apply_shield_batch` is not admitted by `rpc-serve`.

`reports/testnet-orchard-rpc-batch-create/orchard-rpc-batch-create-v0-20260515T111516Z/testnet-orchard-rpc-batch-create.json`
from `scripts/testnet-orchard-rpc-batch-create-smoke`.

from `scripts/testnet-orchard-rpc-malformed-edge-load-smoke`. That run

from `scripts/testnet-orchard-rpc-rate-limit-smoke`. That run proves

## Logs And Retention

Operators must retain:

- `/var/log/postfiat/validator-N/rpc-events.ndjson`
- `/var/log/postfiat/validator-N/stdout.log`
- `/var/log/postfiat/validator-N/stderr.log`
- systemd journal entries for `postfiat-validator-N-rpc.service`

Minimum retention for controlled testnet is the greater of seven days or the
current evidence window. If partial-history pruning is enabled, retain RPC logs
through the archive handoff window so `tx`, `ledger`, and `history-status`
answers can be correlated with archive evidence.

## Edge And Firewall Posture

Do not open the validator RPC port publicly. A public load balancer or reverse
proxy must reach it over loopback, a Unix socket, or a private authenticated
overlay and must enforce:

- connection and request-rate limits;
- request body limits at or below `MAX_RPC_REQUEST_BYTES` (`65536`);
- TLS termination for public Internet access;
- access logs with source IP, method, status, and response class;
- no request rewriting that changes JSON request bodies.

Validator-to-validator plaintext transport likewise binds only to explicit
private-overlay IP addresses. Public topology IPs, DNS names, and wildcard
binds fail closed during deployment staging and process startup. Public routing
to that overlay is an operator misconfiguration, not a supported deployment.

## Verification Commands

Before advertising an endpoint:

```bash
scripts/testnet-rpc-read-alias-smoke
scripts/testnet-rpc-serve-tamper
scripts/testnet-rpc-write-edge-load-smoke   # only for write-edge services
```

The readiness gate requires the read-alias smoke and the P0 gate refuses a
local readiness report that omits it.
