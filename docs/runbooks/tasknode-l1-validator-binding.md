# Connect an L1 validator to Task Node

The L1 binding tool proves control of a registered ML-DSA-65 validator key by
signing an account-bound Task Node challenge. It does not submit a ledger
transaction. The tool and registry are separate from the validator release.

Deployment status is recorded in the operator mission, not implied by this
source document. Task Node must support network `l1-devnet` before connection.

## Operator flow

Sign in to Task Node, open **Settings > Validator**, and copy the L1 connect
command. Run it as root on the Linux x86_64 validator host. The command has a
single-use token that expires after 30 minutes; treat it as private.

```sh
curl -fsSL https://tasknode.postfiat.org/l1-validator.sh | sh -s -- <token>
```

To inspect the script first, download it, read it, then run `sh l1-validator.sh
<token>`. The script's `--discover` option reports only the running node's id
and configured key path; it does not open the key.

The tool finds `postfiat-node transport-validator-serve` in the process table,
uses its exact `--key-file` and `--data-dir`, and reads the public node id from
`node_state.json`. It refuses ambiguous processes or relative paths. It does
not search backup directories. The key must already be a private regular file
with no group/other permission bits, matching the node's file-key convention.

The script downloads a SHA-256-pinned static helper into sealed anonymous
memory, then executes it with networking disabled by `unshare --net`. Root is
needed to create that namespace. The helper uses `crates/crypto_provider`,
zeroizes secret buffers, disables core dumps, and emits only validator id,
public key and signature. The signing step writes no files. Unsupported hosts,
failed isolation or a helper hash mismatch stop before signing.

The dedicated FIPS 204 context is
`postfiat-l1-v2/tasknode-validator-binding/v1`. It is distinct from transaction,
consensus and bridge signature contexts.

## Registry and participation

The public registry is a projection of two agreeing read-only RPC observations.
Task Node must reject registry data older than one hour, unknown/inactive ids,
public-key mismatches, expired challenges and replayed tokens. It must bind
network, chain, validator id and the actual registered public key together.

Participation counts actual `precommit_qc.votes`, never the certificate's list
of committee members. The initial chain exposes no UTC timestamp in blocks;
historical 30-day participation therefore remains unavailable. Unknown scores
are null and reward eligibility is false. The exporter records bounded head
observation intervals for later review; it does not invent historical dates.
L1 rewards require resolution of that evidence limitation and the ordinary
Task Node reward rules. Connecting alone does not grant credit.

## Build and verify

From `tools/tasknode-validator-binding`:

```sh
sh build.sh
cargo test --locked
cargo clippy --locked --all-targets -- -D warnings
npm ci --ignore-scripts
npm test
python3 -m unittest -v test_registry test_operator
python3 registry.py --state /path/to/observer.json --output /path/to/registry.json
```

The Python CLI uses only `status`, `validators` and `blocks` on two loopback
read-only RPC sources (default 49650 and 49651). `--ports` selects different
local sources. Publication is atomic; chain resets, conflicting registries,
broken certificates and missing blocks leave the last publication to expire.
The provided user timer runs every ten minutes and serializes the entire read
and publish operation with `flock`. Installing the timer or TLS route is a
separately approved operator action.

The [wire contract](../../tools/tasknode-validator-binding/CONTRACT-l1-validators.md)
contains the exact Node verification call and payload. The
[test vectors](../../tools/tasknode-validator-binding/l1-vectors.json) were
generated by the repository's crypto provider; their keys and fixed challenge
expiries are test fixtures. `verify-vectors.mjs` checks three positives and four
negatives against pinned `@noble/post-quantum` 0.7.1.
