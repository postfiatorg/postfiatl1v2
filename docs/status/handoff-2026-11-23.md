## Solana deposit: two faults found with a real wallet

1. A browser tab opened before Task Node PR 426 refuses the current server's transaction with "the prepared deposit does not match your request". A reload fixes it.
2. Phantom adds its own assertion instructions to mainnet transactions. The two-signer deposit form (reserved nonce) required the signed message to come back unchanged, so it refused. The relay is temporarily set to the one-signer form, which accepts those edits. That form is valid for about a minute, so the user must confirm promptly.

The fix is [Task Node PR 428](https://github.com/postfiatorg/tasknode/pull/428). It accepts Phantom's edits on the two-signer form under a strict co-signing rule, tells a stale tab to reload, and shows and logs the specific refusal reason. It passes its local checks. It is not merged or deployed, and the two-signer form has not been tried with a real Phantom wallet. After it is deployed and proven, restore the two nonce settings in the relay's environment file and restart the relay.

The headless Phantom test harness does not show this fault. Phantom's simulation service refuses headless browsers, so Phantom adds nothing there. A green harness run is not proof that a real wallet works.

## Solana withdrawal: ordered, in progress

A holder of pfUSDC that came from Solana cannot withdraw to Solana today. Three things are missing on the live network:

1. **The validators cannot encode a Solana withdrawal.** The packet builder for `vault_bridge_burn_to_redeem` accepts only EVM destinations. The Solana encoder exists in the archive (`archive/20261121/private/sol/withdraw`) and never reached `main`.
2. **Exit-route selection is per asset family, and it selects Ethereum.** Solana and Ethereum deposits mint separate series of pfUSDC with separate backing buckets. Selection must become per series, and a Solana exit descriptor must then be approved by governance, without changing what the Ethereum series resolves to.
3. **The exit verifier on Solana mainnet (`8Dxp8bfgEh6ankapfBdkTds5cebqrtPdFxpZSP6JsGAF`) was deployed but never initialised.** Initialising its light client is a one-time step signed with the program's key. It binds one backing bucket.

A payout service and a withdraw screen for Solana are also needed. A Solana exit has so far been proven only in a local simulated bank, never on mainnet or devnet.

Work is on branch `sol/exit-tasknode` in the private archive repository. The plan is: validator change behind an activation height, reviewed, released from `main` and rolled; governance descriptor; program initialisation; payout service; withdraw screen; then a real 0.02 USDC exit with our own funds before anyone is told it works. The founder has approved the governance change and the program initialisation.

## Private payments: two tracks, one decision outstanding

- **Quantum-safe track (PFSH02).** Branch `feat/peel-binius-shielded-pq`, [draft PR 207](https://github.com/postfiatorg/postfiatl1v2/pull/207). Status page: `docs/quantum/private-payments.md` on that branch. Milestones M1 to M5 are done and re-run: shared verifier crate, frozen wire format, isolated per-asset pool, signed shield with private pay and exit for PFT and pfUSDC, and activation that stays off unless a signed height is set. M6 (wallet daemon, key derivation, scanning, CLI) is running. M7 (browser wallet, migration) and M8 (six-validator rehearsal and external cryptographic review) have not started. A payment is about 139 KB and verifies in 21 to 37 ms in a validator. The quantum soundness argument has not had external review.
- **Orchard track.** [Draft PR 206](https://github.com/postfiatorg/postfiatl1v2/pull/206) shows an early version. The current version is on `privacy/transfer-on-main` in the private archive repository: shield, private pay and exit in a pool of its own, a resident prover, and a Task Node wallet tab (branch `wallet/private-payments` on the Task Node repository, off behind a flag). It runs end to end on a local chain. It has had four rounds of review; the last found no missing check in the circuit. It is not quantum-safe.

The founder has said quantum-safe privacy is the goal. Neither track is activated on the live chain, and neither should be until he says which one ships in the Task Node.
